# ADR-025: Support tickets, automatic tickets and review moderation

- **Who can open tickets.** Customers and business owners (`CUSTOMER_CAPABLE`) through `/tickets`, limited to the types `booking_dispute`, `refund_request`, `provider_complaint`, `account_issue`, `other` (`flagged_review` and `failed_notification` are created by the system). Booking disputes and refund requests must name an appointment, provider complaints a business or appointment. A linked object must belong to the requester (customer or owner of the appointment, owner of or customer at the business, author or business owner of the review); anything else is 404 so existence is not leaked. 10 tickets and 30 messages per hour per user, at most 200 messages per ticket.
- **Requester view** shows the public thread only (internal notes never leave the admin API; `from_support` marks staff replies). A reply on a resolved ticket reopens it (`in_progress`, `resolved_at` cleared); a closed ticket is final (409 `ticket_closed`).
- **Statuses**: `open -> in_progress -> resolved -> closed`, plus `resolved -> in_progress` (reopen). Everything else is 409 `invalid_transition`. Assign and status changes need the current `version` (409 `stale_version`) and bump it; messages are append-only and need none. Assignees must hold `tickets.handle`. Every admin action writes one audit entry (`admin.ticket_assigned|status_changed|replied|note_added`) and a `TicketEvent` (the history shown in the detail view). A public admin reply notifies the requester (`ticket_reply`); internal notes and tickets without a requester notify nobody.
- **Priority**: per-type defaults (`TICKET_PRIORITIES`, moved into platform settings in Step 9). The admin list sorts `urgent, high, normal, low` then oldest first by default; sorting is restricted to an allow-list.
- **Metrics**: `first_response_at` is set by the first public admin reply, `resolved_at` when resolved (cleared on reopen). `GET /admin/tickets/stats` covers tickets created in an inclusive Karachi-date range (<= 366 days, default last 30): counts per status, median first-response and resolution seconds.
- **Automatic tickets** are created through `source_key` (unique), so redelivered events create nothing: `review_flagged` (one per flag, from the 6.1 outbox rows, claimed with `FOR UPDATE SKIP LOCKED` and marked processed in the same transaction; a 5-minute beat sweep catches missed events), late customer cancellations (opt-in `AUTO_TICKET_LATE_CANCELLATIONS`), notifications that failed for good (new `notification_failed` event), and payment webhook rejections (new `webhook_failed` event; one `high` ticket per provider and reason per hour so a flood of bad requests cannot flood the queue).
- **Attachments**: the model field exists and the admin API only ever returns attachment *names*, never storage paths; an upload endpoint is a follow-up.
- **Moderation** (`reviews.moderate`): `hide` (visible -> hidden), `remove` (visible/hidden -> removed), `restore` (hidden/removed -> visible); reason 1-500 characters. It calls `reviews.services.moderate_review`, which recomputes the rating aggregate and writes the single audit entry (now with IP), then notifies the author (with the reason) and the business owner (without it).
