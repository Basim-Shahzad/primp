# ADR-017: Provider notifications

- **Template keys.** The plan's names replace the 6.1 owner/customer keys (a data migration `0004_provider_templates` renames templates **and** history rows, adds the new templates and is reversible): `provider_booking_created -> new_booking`, `provider_booking_cancelled -> booking_cancelled_by_customer`, `booking_cancelled -> booking_cancelled_by_business`, `booking_reschedule_declined -> reschedule_request_declined`. New: `booking_rescheduled_by_business`, `reschedule_request_accepted`, `booking_reassigned`, `new_review`, `pending_escalation`, `onboarding_status_changed` (the two `provider_*reschedul*` owner keys keep their names). `seed_data.py` stays the source for `post_migrate` re-seeding. Templates are rows, editable without a deployment (admin UI: Plan 6.3).
- **Who gets what** (in-app copy always, external channels per recipient): created -> owner `new_booking` (+ customer `booking_received` when pending; none for manual bookings, which the owner entered); confirmed -> customer; cancelled by business (incl. decline, staff change, auto-cancel) -> customer, with `Reason: ...` when the owner gave one; cancelled by customer -> owner; customer reschedule -> customer + owner; owner reschedule -> customer `booking_rescheduled_by_business`; accepted request -> customer `reschedule_request_accepted`; declined -> customer `reschedule_request_declined`; reassigned -> customer; completed -> customer `review_prompt`; no-show -> nobody; review created -> owner `new_review`. Walk-in bookings without an account notify no customer.
- **Owner preferences** exist per owner event (`OWNER_EVENTS`): `sms` and `email` toggles with defaults `new_booking`/cancel/reschedule/review = email only, `pending_escalation` and `onboarding_status_changed` = SMS only. The dashboard (in-app) copy is always delivered and cannot be disabled. A toggled channel with no contact on file is skipped. **Customer-facing templates ignore preferences entirely** (transactional); preferences only apply to keys in `OWNER_EVENTS`.
- **Owner feed**: `GET /provider/notifications` (cursor, newest first, `unread_count`, `unread_only`) lists the owner's own in-app rows for owner events; text is rendered with one template query per page. `POST /provider/notifications/read` takes exactly one of `ids` or `all`; ids that are not the caller's are ignored (never an error, never updated).
- **Failure handling** reuses the 6.1 dispatcher (exponential retries, SMS->email fallback). A notification that fails for good (no fallback available or the fallback also fails) is flagged `admin_flagged` (status `failed`); `feed.failed_for_admin()` is the selector Plan 6.3 will surface. A failure that was handled by a successful fallback is not flagged.
- Events are emitted on commit, so a rolled-back change sends nothing.
