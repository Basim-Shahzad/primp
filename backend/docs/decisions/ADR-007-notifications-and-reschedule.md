# ADR-007: Notifications, reminders, cancellation and reschedule

- Each notification picks one primary channel (SMS if the user has a phone, else email) plus an in-app row. If SMS fails permanently, or transiently after the 4th attempt, an email notification is created as a fallback; with no email the row is marked `failed` for admin review. Retries use exponential backoff (30 s, 60 s, 120 s) on the queue of the template (`critical`: OTP and booking status, `default`: reminders and provider notices, `bulk`: review prompts).
- OTP codes are rendered from the `otp` template but sent without a log row so codes are never stored in the notification table.
- Reminders: a beat task runs every 5 minutes. A reminder is due while `start - offset <= now < start - offset + grace` (grace 30 min, configurable), only for confirmed bookings that already existed when the window opened. A unique `(appointment, kind)` row claims each reminder so it is sent once even with concurrent scanners.
- Template problems record a failed notification; in tests (`NOTIFICATIONS_RAISE_ON_RENDER_ERROR`) they also raise so typos fail loudly.
- Customer cancellation inside the notice window is allowed and flagged `is_late_cancellation`; the boundary itself (exactly `notice` hours before) is not late. Cancelling after the start time is refused.
- Reschedule: the customer holds a new slot (`POST /appointments/hold` with `appointment_id` so the booking does not block its own replacement) and calls `PATCH /appointments/{id}/reschedule`. Instant-confirm businesses apply it at once. Manual-confirm businesses get a `RescheduleRequest` (one pending per booking) that does not reserve the new slot; `accept_reschedule` re-validates availability, `decline_reschedule` keeps the original time. Both are service functions for Plan 6.2 to expose.
