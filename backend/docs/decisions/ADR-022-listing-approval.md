# ADR-022: Listing approval queue

- **Queue items** (`ReviewQueueItem`, public UUID id) are created by event consumers for `business_submitted` (kind `new_listing`) and `business_change_review_requested` (kind `change_request`). A DB constraint allows one non-closed item per (business, kind), so a duplicate event delivery is a no-op; a resubmission creates a new item once the previous one is closed; later change requests merge into the open one.
- **Concurrency.** Every decision locks the item row and checks, in order: closed -> 409 `item_closed`; `version` mismatch -> 409 `stale_version`; claimed by another admin -> 409 `already_claimed`. Each successful claim/decision bumps `version`. Two admins deciding at once serialise on the row lock, so exactly one wins and the loser gets 409; the business state change and the decision commit together or not at all.
- **Decisions reuse the Plan 6.2 verification service** (`mark_verified`, `reject`, `request_more_info`, `revoke_verification`) and two new functions there: `approve_pending_changes` (applies name/slug/category, refuses an inactive category) and `reject_pending_changes`. Those functions already write the audit entry, so a decision produces **exactly one** `AuditLog` row; the 6.2 functions gained optional `ip` and `context` arguments (queue item id, checklist) so that row carries the IP and the checklist.
- **Checklist**: `identity_matches`, `address_plausible`, `photos_genuine`, `category_correct`, `no_duplicate`. Approval requires all five true (422 `checklist_incomplete` naming the failed ones); reject/request-info accept it optionally. It is stored on the `ReviewDecision` row and in the audit entry.
- **Detail view**: the public preview (same renderer as the public page), private fields (owner contact, address, submissions with terms version and IP, pending changes), duplicates, decisions, notes and earlier items. Documents are included only for actors with `documents.view` as signed links advertised as valid for at most 5 minutes, never as storage paths; each view that includes documents writes one `admin.documents_viewed` audit entry.
- **Duplicates**: same phone/WhatsApp as another business, or within `DUPLICATE_DISTANCE_METERS` (30) and a name with trigram similarity >= `DUPLICATE_NAME_SIMILARITY` (0.5). CNIC numbers are not captured by the platform, so there is no CNIC check.
- **Revocation** (`businesses.revoke` + re-authentication) calls `revoke_verification` directly; it is not a queue item.
