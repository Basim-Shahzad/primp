# ADR-026: Promotional banners

- **Lifecycle.** A banner is created disabled with a title, optional subtitle, a validated link, a start/end window (aware datetimes, `ends_at > starts_at`, also a DB check) and an optional city (null = every city). Desktop and mobile images are uploaded separately (re-encoded, metadata stripped, 1600 px / 800 px) and a banner cannot be **enabled** until both exist (422 `images_required`). `PATCH`/`DELETE` need the current `version` (409 `stale_version`); each change, image upload, delete and reorder writes one audit entry. Reordering takes the complete list of banner ids (a permutation). Replaced and deleted image files are removed after commit.
- **Links** must be `https://host/...` without credentials, or an internal path starting with a single `/`. `javascript:`, `data:`, `vbscript:`, `http:`, protocol-relative `//host`, backslashes, whitespace and control characters are all rejected.
- **Public feed** `GET /banners?city_id=`: enabled banners with both images whose window contains *now* (`starts_at` inclusive, `ends_at` exclusive), city-specific ones for that city plus all-city ones; without `city_id` only all-city banners. No scheduler: the cache (60 s) holds the *enabled candidates* and the window is applied at read time, so boundaries are exact; every admin change bumps a version that is part of the cache key, so changes show at once.
- **Tracking** `POST /banners/{id}/impression|click` (public, 204): counted with Redis `INCR`; only live banners are counted (404 otherwise); 30 per minute per IP, banner and kind (429). A beat task (`banner-counter-flush`, every minute) moves the counts into the database with `GETDEL` + `F()` updates inside a transaction; running it twice adds nothing, and a failed database write puts the counts back. If Redis is down tracking degrades to a direct database increment. Admin lists show database + pending counts.
