# ADR-020: Admin roles, permissions and re-authentication

- **Groups.** Three Django `Group`s (`support_agent`, `ops_admin`, `super_admin`) hold the permissions of the plan's table. Permissions are real `auth.Permission` rows (codenames such as `users.view`) attached to an unmanaged anchor model `backoffice.AdminPermission`; a data migration and a `post_migrate` hook create them and the groups idempotently (a test flush wipes them).
- **Who counts as an admin.** `User.role` is `admin` or `super_admin`. A `super_admin` *role* holds every permission without needing the group (so the last super admin can never lock themselves out through group edits); an `admin` holds the union of their groups' permissions. Customers, owners and staff hold none, so they get 403 on every admin endpoint; anonymous or invalid tokens get 401.
- **Checks.** Endpoints call `require_permission("x.y")(request)` which returns an `AdminActor` (user, permissions, session id, IP). Services receive the actor and call `actor.require(permission)` again, so the Django admin and the REST API share the rule. High-risk permissions (`users.suspend`, `businesses.revoke`, `points.adjust`, `config.manage`, `admins.manage`) additionally require a re-authentication in the last 15 minutes (403 `reauth_required`).
- **Re-authentication** is stored per session (refresh-token family id from the access token's `sid`) as an exact timestamp in the cache, so it is testable with a frozen clock and a second session of the same admin is unaffected. `POST /admin/reauth` checks the password (5 tries per 15 minutes per admin, failures audited). A fresh `POST /admin/auth/login` counts as re-authenticated.
- **Admin login** (`/admin/auth/login`) is a password login that only admits admin roles (anyone else looks like wrong credentials and their new session is revoked) with a stricter per-IP throttle. Admin access/refresh lifetimes are the shorter ones from Plan 6.1.
- **2FA** is not implemented; see FOLLOW_UPS.
