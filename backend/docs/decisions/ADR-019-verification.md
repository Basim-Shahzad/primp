# ADR-019: Verification state machine and badge

- **Service functions** in `businesses/verification.py`, called by the Plan 6.3 admin endpoints (only `admin` / `super_admin` accepted, else 403): `mark_verified`, `revoke_verification`, `request_more_info`, `reject`. Each locks the business row, validates the edge, writes an audit entry with before/after snapshots (`status`, `is_listed`, `status_message`, `revoked_reason`, `verified_by`), emits `business_verification_changed`, notifies the owner (`onboarding_status_changed`, with the admin's message) and calls `touch()`, which drops the cached public page, the next-slot cache and queues frontend revalidation.
- **Allowed edges** (anything else is 409 `invalid_transition`): `pending -> verified | needs_info | rejected`; `needs_info -> rejected`; `verified -> revoked`; `revoked -> verified` (reinstate). Messages for revoke / more-info / reject are mandatory (1-500 characters, 422 otherwise).
- **Effects**: approval lists the business (`is_listed = True`), stamps `verified_at` / `verified_by` and clears messages. More-info and rejection keep it unlisted. **Revocation removes the badge only**: `is_listed` is left as it was (a separate suspend/delist action is an admin decision for Plan 6.3), and the reason is shown to the owner as `revoked_reason` and `status_message`.
- **Badge exposure**: `is_verified` on the public page, search items and the owner payload is derived from `verification_status == verified` only; `verified_only` filters on the same column, so a revocation is visible in both on the very next read.
- A revoked business is not owner-editable through onboarding (it can only be reinstated by an admin).
